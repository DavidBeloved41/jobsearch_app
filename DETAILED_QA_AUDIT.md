## ISSUE 6: DUPLICATE PREVENTION NOT ATOMIC ⚠️

### Problem

The duplicate check and insert are NOT atomic:

```dart
// Step 1: Check for duplicate (SELECT)
final existingApplication = await _client
    .from('applications')
    .select('id')
    .eq('user_id', userId)
    .eq('job_id', jobId)
    .maybeSingle();

if (existingApplication != null) {
  throw StateError('You have already applied for this job.');
}

// Step 2: Insert (INSERT)
await _client.from('applications').insert(applicationData);
```

**Race Condition**: Between step 1 and step 2, another instance of the app could insert a duplicate.

### Proper Fix

Use database-level UNIQUE constraint:
```sql
ALTER TABLE applications
ADD CONSTRAINT unique_user_job_application
UNIQUE (user_id, job_id);
```

Then if a duplicate is attempted, the database will reject it with:
```
PostgreSQL Error: "duplicate key value violates unique constraint"
```

This error should be caught and converted to user-friendly message.

## ISSUE 8: RESUME STORAGE PATH INCONSISTENCY ⚠️

### Problem

In `resume_screen.dart:257`:
```dart
final fileName = '$userId/resume.${file.extension}';
await Supabase.instance.client.storage
    .from('resumes')
    .uploadBinary(
      fileName,
      file.bytes!,

```

But when deleting (lines 350-360):
```dart
for (final ext in ['pdf', 'doc', 'docx']) {
  final fileName = '$userId/resume.$ext';
  try {
    await Supabase.instance.client.storage.from('resumes').remove([fileName]);
  } catch (e) {
    debugPrint('Could not delete $fileName: $e');
  }
}
```

### Potential Issue

The upload uses `file.extension` which could be:
- `pdf`, `doc`, `docx` (expected)
- But also potentially: `PDF`, `DOC`, `DOCX` (uppercase)

The delete loop ONLY tries lowercase extensions!

### Example Failure Scenario

1. User uploads `Resume.PDF` (uppercase)
2. File stored as `userId/resume.PDF`
3. User clicks delete
4. Delete loop tries: `resume.pdf`, `resume.doc`, `resume.docx` (all lowercase)
5. None match → file stays in storage
6. User uploads `Resume.pdf` again
7. `upsert: true` should overwrite, but...

If the previous PDF still exists, there might be a collision.

### Fix Required

Normalize file extension to lowercase:
```dart
final fileName = '$userId/resume.${file.extension.toLowerCase()}';
```

## ISSUE 9: JOB MATCHING ALGORITHM - SKILL NORMALIZATION ⚠️

### Implementation Analysis

In `match_score_service.dart:50-65`:
```dart
final jobText = [
  job['title'] as String? ?? '',
  job['description'] as String? ?? '',
].join(' ').toLowerCase();

if (skills.isNotEmpty && jobText.isNotEmpty) {
  for (final skill in skills) {
    final name = skill.trim().toLowerCase();

    } else {
      missingSkills.add(skill);
    }

```

### Issues

1. **Simple substring matching**: "flutter" matches "flutter development", good.
2. **But**: "api" matches "replay", "happy", any word containing "api"
3. **No stemming**: "developing" vs "developer" not matched
4. **No normalization**: "C#" vs "csharp" not matched

### Example Failures

Job: "We need Flutter, REST API, and Firebase"
User skills: ["Flutter", "REST API", "Firebase", "SQL"]

Results:
- "Flutter" → matches "Flutter" ✓
- "REST API" → matches "REST API" ✓
- "Firebase" → matches "Firebase" ✓
- "SQL" → does NOT match "REST API, Firebase" ✓

Works correctly in this case.

But:

Job: "Developing Node.js APIs with Firebase"
User skills: ["API Development", "Node", "Firebase"]

Results:
- "API Development" → matches "APIs" ✓ (substring match works)
- "Node" → does NOT match "Node.js" ✗ (FAILS - should match!)
- "Firebase" → matches "Firebase" ✓

### Fix Required

At minimum, improve skill matching:
```dart
bool skillMatches(String skill, String jobText) {
  final skillLower = skill.toLowerCase();
  final skillWords = skillLower.split(RegExp(r'[^\w]+'));
  
  // Try exact substring match first
  if (jobText.contains(skillLower)) return true;
  
  // Try matching individual words
  for (final word in skillWords) {
    if (word.length >= 3 && jobText.contains(word)) {
      return true;
    }
  }
  
  // Try normalized forms
  final normalized = {
    'node': ['node.js', 'nodejs'],
    'c#': ['csharp', 'c sharp'],
    'c++': ['cpp', 'c plus plus'],
  };
  
  if (normalized.containsKey(skillLower)) {
    for (final alt in normalized[skillLower]!) {
      if (jobText.contains(alt)) return true;
    }
  }
  
  return false;
}
```

## ISSUE 11: ADMIN AUTHORIZATION - HARDCODED EMAIL ⚠️

### Implementation

In multiple routes, admin is checked via:
```dart
final isAuthorized = currentUser?.email == 'beloveddavid41@gmail.com';
```

### Security Concerns

1. **Not flexible**: Adding another admin requires code change
2. **Email verification**: What if the email isn't verified?
3. **No audit trail**: No way to see who performed admin actions
4. **Phone auth**: What if admin signs up via phone instead?

### Better Approach

Should check a field in the profiles table:
```dart
CREATE TABLE profiles (
  ...
  account_type TEXT CHECK (account_type IN ('job_seeker', 'employer', 'admin')),
  ...
);

// In Flutter:
final profile = await SupabaseService.getProfile(userId);
final isAdmin = profile?['account_type'] == 'admin';
```

This allows admins to be managed in the database without code changes.
